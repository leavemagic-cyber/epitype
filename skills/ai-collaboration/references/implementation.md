# 實作模式

先確認現行要求、驗收條件、寫入範圍與正式 repo 的整合者。沿用有效設計，只有方案未定才進入討論模式；不為每項實作強制多方辯論。

1. 依使用者指定及專案當前分工選作者、非作者審查者。沒有指定的日常實作由現有 lead 負責；不要固定換 Claude、Codex 或 Gemini。
2. 作者讀相關實作與呼叫者，在獲授權的範圍改動並跑適當檢查。外部作者需獲授權的隔離工作目錄；正式 repo 寫入限制照 host／專案規則。
3. 送審時才讀同目錄 [審查模式](review.md)，用確切 diff、相關檔案及實際驗證結果交給非作者審查者。真缺陷修好並查證，避免回傳整份歷史。
4. 依授權提交明確路徑，署名只記實際作者與審查者。不得套用固定專案路徑、自動更新其他 checkout 或憑 APPROVE 宣稱已部署。
5. 任務包含啟用時，另查實際讀入路徑與效果；交付記錄結果與必要限制。

專案角色及工具由當前專案的入口或 handoff 提供；見 [專案參考](project-overrides.md)，不能變成所有專案的預設。
