# 多方交叉質詢

這是同一協作 skill 的質詢步驟，人數依當次名單，不要求每次四家。四方保留既有 Claude 主席情境：Claude 主持並兼一席，Codex、Grok、Gemini 是外部席，owner 為第五方。其他情境依當前使用者指定與主責，不為套表換主責。

## 開題與初輪

在專案紀錄位置建立 `BRIEF.md`：題目、工作目錄／版本、檔案、有效要求與範圍、驗收、背景證據、已排除方向及系統關係。大題切成能恢復的小塊，各塊仍可查整體接口。

原話只作必要備查；實質歧義或衝突才回查，不是開工或修改門檻。owner 的有效決定可被挑戰，屬其專屬取捨才交其改；新指示已改要求就直接照做。AI 整理不能冒充逐字授權。

1. 主持者先存 `CHAIR_R1.md`，再看其他人回答。作者不冒稱自己的獨立審查者；只有現有授權允許時才另派非作者。
2. 用 [R1](../templates/R1.md) 建題。各席能查完整相關檔案與底層證據，初輪只隱藏其他人的答案。
3. 寫 `MERGED.md` 去重並標來源及重要分歧；此摘要不取代下一輪要看的完整回答。

## 互質與裁定

4. 用 `seats.py bundle` 與 [R2](../templates/R2.md) 組題，送達所有實際參與者的初輪全文，包括主持者。各席逐項 `AGREE`（查了什麼）、`CHALLENGE`（反證）或 `COUNTER-PROPOSE`（更好的做法），撤回被推翻主張。主持者存 `CHAIR_R2.md` 回應挑戰。
5. 主持者親查重要、爭議項目的程式／來源／測試，在 `RULING.md` 逐項記採用、不採用或真正需要 owner 決定，附證據和理由。票數不是證據。要改 owner 專屬決定時，交代現行決定、改法、證據、得失與建議；缺歷史原話不增加批准門檻。
6. 用 [R3](../templates/R3.md) 組合前兩輪全部回答與裁定全文。各席可 `OBJECT` 並附未考慮的新證據，否則 `NO OBJECTION`；主持者逐條查證。裁定與 R2 每席一致，且沒有不採用／交 owner 項目時可省 R3 並說明。
7. 只有新證據需要他席確認才追加該點；修正後查受影響處，真缺陷未解就續做，不為形式重播無關材料。

完整回答是交叉質詢材料要求，不要求全文載入使用者歷史對話。討論結論需落地，實作與審查需查實際結果，不以派題、回報或投票當完成。
