# 只帶入目前專案的資料

優化目標是讓對話拿到目前專案需要的資料，並保留真正共用的規則。
多找到或多送出幾張卡，不能單獨代表這個目標已達成。

## 如何選擇

有 `cwd` 的一般喚回先搜尋目前目錄及祖先對應的原生記憶庫，再搜尋共用治理庫。
共用庫可能保留其他專案的舊卡或連結，因此還需要逐卡檢查範圍：

1. 有 `rule_provenance` 的卡，沿用來源驗證及其中經審查的 `scope`。明確不屬於本場專案或案件的卡不送出，檢查發生在優先排序及名額計數之前。
2. 一般查找資料可在 frontmatter 宣告 `project`。建議使用專案根的絕對路徑，讓 hook 提供的 `cwd` 可以直接比對。
3. 舊的 `reference`、`project`、`pending` 卡若只有正文中的明確宣告，也能使用下方相容格式。這是讀取既有範圍，不會搬動卡片或改寫連結。
4. 在用卡片的連結找相關資料前，先套用同一套准入檢查。其他專案、來源不合格、原話事件或已暫停喚回的一般卡，不能間接把鄰接卡帶進對話。有效卡片的一層連結，以及其他卡片自身的直接、別名、完整原話命中仍保留。

```yaml
---
name: project-reference
description: 本專案的環境資訊
project: /absolute/path/to/project
metadata:
  type: reference
---
```

Windows 路徑同樣可用，例如 `project: C:\work\example`。
舊卡正文的相容格式為：

```markdown
**適用專案**：`/absolute/path/to/project`。
```

英文標籤可用 `**Applies to project**:`。正文須有唯一、明確的絕對路徑宣告；
程式碼區塊、引用、相對路徑、多個或相互衝突的宣告不據以排除卡片。
正文相容檢查最多讀取 64 KiB；讀不完整或讀不到時保留查找線索。

## 保留的邊界

- 已驗證來源的範圍優先於舊正文與一般 `project` 欄位，不能藉舊欄位藏掉全域規則。
- 不從卡片建立時的工作目錄、專案名稱的相似度或一般正文推測適用範圍。
- 缺少本場專案資訊、只有無法比對的專案名稱，或 Git 身分查詢失敗時，保留資料並視為範圍未確認。
- 路徑按目錄邊界比對，不把 `example-other` 當成 `example` 的子目錄。範圍比對可辨認同一 Git repo 的 worktree，並保留 monorepo 子目錄的界線。
- 壓縮後的卡片恢復也使用相同檢查，避免舊指標把另一專案資料重新帶回來。
- 沒有 `cwd` 的舊事件仍沿用搜尋已設定各庫的相容行為；本次沒有改成猜測專案。

一般喚回的張數及 byte 預算不變，來源驗證、繼任卡解析與人工搜尋也不變。
排除外部專案卡後，其他符合條件的卡可能補上名額，所以這項修復不保證總 bytes 一定變少。
應分別檢查混入是否消失、正確專案是否仍可取用，以及實際注入量。

連結展開只使用原本排名前三的文字命中，不會往後補更多起點或遞迴展開。
只有實際要沿連結擴展時才檢查起點；同一次 hook 的來源結果共用，避免搜尋與送達各驗一次。
一般人工搜尋不套用這個對話准入回呼，仍可用舊卡追查相關資料。
